Transport: raw RFB over WebSocket (track 1)¶

Appendix C of solution.md · Status: adopted as component [G] (solution.md §3.2, §4) · Links checked 2026-10-10.

1. Summary¶

Decision: our own Python process speaks raw RFB (VNC) over WSS to the target's /websockify endpoint, using the websockets library. No browser is involved. Implementation: poc/rfb_poc.py.

Terminology. websockify is the server-side proxy the target already runs: it accepts a WebSocket and forwards the bytes over TCP to the VNC server. We didn't choose it and can't change it. On our side the client library is websockets (Python). People mix the two up, so expect the question in the debrief.

2. Problem and constraints¶

Source: Appendix B.

our process ──WSS /websockify──► websockify ──TCP──► VNC server (Docker 86a79607eef2:0) ──► SIGECOM
  • Protocol: RFB 3.8 with VNC Authentication (DES challenge-response). There's no HTTP auth and no cookies.
  • The app has no DOM and no API. The host exposes only /health and /websockify.
  • noVNC in a browser is just one RFB client. Anything that speaks RFB through a WebSocket can take its place.

The decision therefore has two layers: - A. Where the RFB client runs: inside a browser (noVNC) or inside our own process. - B. If it runs in our process: which language, which WebSocket library, and whether we write the RFB code ourselves or use a VNC library.

3. Options considered¶

3.1 Layer A — where the RFB client runs¶

Option How it works Pros Cons Verdict
A1. Raw RFB client over WSS Our process opens the WSS connection, does the RFB handshake, keeps the framebuffer as a numpy array, and sends pointer and key events
  • Pixels are lossless because we choose the encodings (Raw and CopyRect).
  • The framebuffer lives in memory, so a screenshot needs no network call.
  • Click coordinates are framebuffer coordinates: no canvas offset, no scaling.
  • Every FramebufferUpdate reaches us, which gives the settle and change-detection signal for free.
  • We can use the clipboard channel (ClientCutText / ServerCutText) directly.
  • One process and no Chromium, so the Railway deploy stays small.
  • Per-task {url, password} are plain constructor arguments.
  • About 200 lines of code, already working.
  • We own the protocol code: handshake, encodings, reconnect.
  • Only VNC auth is implemented.
 Chosen
A2. Playwright/Chromium + the noVNC page A headless browser loads /vnc.html?autoconnect=1&password=…. We screenshot the canvas and click with page.mouse
  • No protocol code to write.
  • noVNC already handles every encoding and auth type.
  • We see exactly what a human sees.
  • Frames arrive as Tight/JPEG (observed in the analysis), and the artifacts hurt OCR and pixel diffs. ?quality=9 helps, but the default stays lossy.
  • Canvas offset and scaling: changing the viewport shifted the image by +160 x / +100 y in the analysis, so every click needs a coordinate translation.
  • Each screenshot is a canvas-to-PNG encode plus a CDP round trip (tens to hundreds of ms), compared with reading an in-memory array.
  • Settle has to be inferred by polling the DOM or canvas, or by hooking noVNC's JS.
  • Chromium adds about 300 MB to the image, more RAM and a slower cold start, all inside a 5-minute task budget.
  • Two layers can fail: the browser and VNC.
 Discarded: it costs fidelity, latency and deploy size and gives the agent nothing it needs
A3. Playwright driving noVNC's JS API page.evaluate(...) calls rfb.sendKey and reads canvas.getImageData
  • Lossless reads and exact coordinates.
  • Every browser cost of A2, plus a JS bridge to maintain.
  • In effect it's A1 with a browser wrapped around it.
 Discarded: strictly worse than A1
A4. Local bridge + an off-the-shelf TCP VNC client websocat --binary tcp-l:127.0.0.1:5900 wss://host/websockify, then asyncvnc, vncdotool or TigerVNC connects to localhost
  • Mature VNC libraries. asyncvnc gives numpy frames, the clipboard and many encodings.
  • An extra binary and process to deploy and supervise for each task.
  • Two sockets to reconnect.
  • The libraries hide the update stream (vncdotool is Twisted-based and polls), so we lose the per-update settle signal.
 Fallback, if the unseen app's server needs an encoding or auth type our code lacks
A5. Computer-use VM (Anthropic reference container with xdotool) Run a desktop locally and open the noVNC page in it
  • Works with Claude's computer-use tool out of the box.
  • It's A2 with a full desktop on top: the heaviest option.
 Discarded
A6. Another protocol (RDP, SSH, an app API) — — Not exposed: the host serves only /health and /websockify, and the unseen app is delivered the same way N/A

3.4 Layer B — VNC libraries instead of our own RFB code¶

  • asyncvnc / asyncvnc2: asyncio-based, numpy frames, clipboard support. But they connect over TCP through asyncio streams, so we'd need A4's bridge or a patched stream. They also hide FramebufferUpdate timing (our settle signal) and the choice of encoding.
  • vncdotool: Twisted-based and CLI-oriented. It's TCP-only; the noVNC maintainer confirms it can't connect to a WebSocket-only endpoint.

4. Chosen design¶

A raw RFB client in our own process (A1), in Python, on websockets, with our own protocol code. The verdict column in §3 gives the reason for each.

Why Python. The transport is the smallest part of the system. Perception (track 2), the executor and tools (track 3), and the entrypoint (track 5) all depend on Python's image and ML ecosystem. Keeping everything in one language and one process means no IPC. Raw speed doesn't matter here: the native framebuffer is 1280×800 (measured), so a full Raw frame is about 4.1 MB, incremental updates are small, and numpy slicing is far cheaper than the network. Node's one real advantage, reusing noVNC's rfb.js, is cancelled out by that code's DOM coupling.

  • Our own code: about 150 lines of protocol. We control the encodings (lossless) and see every update, so nothing hides inside the 5-minute budget.
  • Risk: the unseen app's server may use an encoding or auth type we don't handle.
  • Mitigation: we only request Raw and CopyRect, and every RFB server must support Raw. A4 stays as the fallback.

5. Trade-offs we accept (say these in the debrief)¶

  • Bandwidth. Raw is the most expensive encoding. SIGECOM's UI is mostly static, so this is fine for now. Measure it in 1.4. If it hurts, add Tight with JPEG turned off (lossless zlib) rather than JPEG.
  • We own reconnect (1.2), settle (1.3) and clipboard send (1.6). Each is a small, listed unit.
  • Auth. We support VNC auth (type 2). Adding type 1 (None) is trivial. VeNCrypt and RA2 are out of scope, and the design doc states that as an assumption.

6.1 Reading the numbers¶

  • Connecting costs about 4 s, up to 6 s per task, which is 1–2% of the 5-minute budget. Open the connection once per task and reuse it; never reconnect per action.
  • About 2.2 s of that is the first 4.1 MB Raw full frame. This is the bandwidth cost of lossless pixels. Incremental updates after that are small. If cold start matters, try Tight with JPEG off (lossless zlib) in 1.4.
  • The native resolution is 1280×800, not the 1258×566 canvas noVNC showed. A2's browser view was scaled or cropped, which is one more argument for A1's exact coordinates.
