Frontier Challenge 1 — Solution¶

The agent that operates what has no API. This is the one document: sections 0–11 are the design, and the appendix table at the end points at the brief, the recon and every research doc, kept in full in resources/docs/appendixes/. solution.html renders this document, the architecture diagram and all appendixes in full; uv run resources/docs/build_html.py regenerates it.

0. One-page summary¶

Problem. A 15-year-old management system with no API, no docs and no vendor. The evaluator sends a natural-language task plus a VNC desktop (URL + password) and expects a result within 5 minutes. Evaluation runs on an app we have never seen, on a clean desktop, and the app changes at 15:30.

Approach. Our own Python process speaks raw RFB (VNC) over WebSocket to the desktop. A task is a natural-language CRUD action: one fast-model call splits it into typed queries, and a deterministic executor answers reads from a SQLite cache behind a freshness probe and replays learned procedures for writes, clicking stored positions as long as the pixels still match. Perception (CPU-only OCR + classic CV) runs only when something changed, Jev answers the typed questions a changed screen raises, and the tool-use loop, which picks named elements, never coordinates, is the last resort. Everything the agent learns about an app (screens, app map, procedures, data) is a per-app memory built at run time, so the unseen app is handled exactly like SIGECOM: its first task perceives and learns, every later task replays. For SIGECOM the same memory is built ahead of time (map --visit, seed) and ships in the image. The 15:30 change is detected by expected-edge checks and repaired locally inside the task.

What makes it work on an unseen app 1. No hand-coded map: perception + a learned app map keyed by the app's title bar. 2. Semantic targets (label + role + grid cell) with the last click point that worked cached beside them: replay clicks it while the pixels match, finds a moved target by template match, and re-grounds by perception only on a miss, so a moved or renamed button still works. Each screen and target keeps one appearance per app version, and the map is frozen per epoch, so a redesign adds a version instead of breaking memory. 3. A disposable SQLite read cache behind a freshness probe (the app's own change log when it has one, like SIGECOM's Bitácora de cambios), so lookups answer in seconds instead of OCR-paging every time. 4. A parse → replay → verify executor with a 270 s guard that always writes a summary; the tool-use loop runs only when there is nothing to replay. 5. One JSONL log of every step, which feeds the Challenge 2 spec, the debrief and the eval harness.

Eight decisions (full table in §4): raw RFB instead of a headless browser · lossless Raw+CopyRect · hybrid OCR+CV perception with Set-of-Mark · learned per-app map instead of a hand map · export/clipboard before OCR for data · online localized repair instead of a full re-learn · replay and probe first, perception on change, the tool-use loop last · every model through OpenRouter, Jev for typed decisions.

Measurement. About 15 NL tasks on SIGECOM: the 5 official practice tasks E1–E5 (create, update, count question, export, an ambiguous name that must fail) plus about 10 of our own (lookup, filter, create, edit, export, multi-screen), scored by the desktop's own POST /__check oracle plus checks on status and summary. Metrics: success %, time per task, steps per task, click hit rate, drift detected/recovered. Baseline before 15:30, re-run after, plus a map-mutation suite that simulates the change in advance (§6).

1. Problem and constraints¶

Inputs we have. The brief (Appendix A), the recon of the target (Appendix B: noVNC → websockify → RFB → SIGECOM shown only as pixels), and poc/rfb_poc.py, which already speaks raw RFB with no browser: VNC auth, Raw+CopyRect frames, click/type/key, quiet-time settle, and 4 tool functions (screenshot/click/type/key). See Appendix I.

The entrypoint contract (Appendix A): Authorization: Bearer <token> on every call; GET /health → 200; POST /tasks receives the task and the desktop (URL + password) and must answer {"task_id": …} in under 2 s; GET /tasks/{task_id} returns en_curso / terminada / fallida plus a summary; 5 minutes per task. The summary carries one respuesta: <value> line for a question (a number first, two values joined by ;, no line when unanswerable), names the data behind a fallida, and never repeats the desktop password or any other secret. After the final status the agent stops acting: anything later lands in the next task as an out-of-task change. Full rules in Appendix A §6.

The constraint that shapes everything: evaluation runs on an app we have never seen, on a clean desktop, with 5 minutes per task, and the app changes at 15:30. So "mapping" can't be a hand-built coordinate map of SIGECOM. It has to be something the agent learns while it runs. SIGECOM is only for development.

Deliverables and timeline (Appendix A): design doc + diagram at 12:00, the change in the system at 15:30, deployed entrypoint, repo and 2-minute video at 20:00, individual debrief 20:00–21:00, demo 21:15–22:15.

2. What we operate against¶

Digest of the recon in Appendix B:

  • The URL serves the noVNC web client, not a web app. The business system, SIGECOM · Distribuidora Andina v3.9, runs inside a remote desktop and reaches the browser only as framebuffer pixels. No DOM, no REST, no HTTP login.
  • Only two live endpoints: GET /health → {"ok":true} and the /websockify WebSocket upgrade. Everything else is 404.
  • Wire: browser → wss://…/websockify → websockify proxy → TCP RFB 3.8 → VNC server in a Docker container (86a79607eef2:0). Auth is VNC Authentication (DES challenge-response). Native framebuffer is 1280×800.
  • The desktop is shared: the user label flipped between operador and operador2, so a human or another client may be on the same display.
  • SIGECOM menu tree: Archivo › Inicio · Comercial › Maestros › Clientes, Ventas › Pedidos · Cartera › Facturas · Herramientas › Bitácora de cambios, Reportes generados, Configuración › Integraciones · Ayuda › Acerca de. Facturas has filters (Cliente, Estado), Buscar / Limpiar / Exportar, a grid (Código, Cliente, Fecha, Vence, Valor, Estado) and Anterior · Página 1 · Siguiente.
  • From the organizers (Appendix A §5): a screen repaints up to 1 s after a click, a click held under 100 ms is ignored, and typing into a non-empty field concatenates, so every fill selects all first. The desktop also exposes POST /__reset (reload the seed data) and POST /__check (score a practice task against the app's state).
  • Integraciones shows an accounting-connector key with "No comparta esta clave": denylisted.

3.3 Per-task flow¶

  1. POST /tasks {task, desktop:{url,password}} → validate Bearer → store en_curso → return task_id.
  2. Runner opens an RFB session [G] with the given URL+password and takes the first screenshot.
  3. [E] fingerprints the screen and identifies the app (title bar) → [F] loads the map for that app and version if one exists, inherits the previous version's map as hints if only the version is new, otherwise starts cold (first task on an app or on a new version: ≤ 45 s menu pre-warm, Appendix E §4.3).
  4. [C] splits the task into typed CRUD queries with one fast-model call. The executor runs them on the one screen in schedule order: cache hits first, then grouped by entity, keeping the parsed order of a write and any query on its entity; answers are reported in the order asked. Reads go change-log probe → [DB] cache → SQL (on a miss, the [S] ladder); writes replay the stored procedure for that (op, entity) with the query's fields. Every step: observe replays the stored bbox while the static pixels match (a target that only moved is found by template match) → act → settle → compare with the edge's expected effect → return the observed effect. Perception runs only on a changed screen.
  5. Unexpected screen / no effect → [E] flags drift → [F] marks the node stale → [C] runs the repair ladder (§6): Jev picks the new target from the element list, the VLM when Jev is unsure, local re-explore, replan. The tool-use loop with MODEL_PLANNER takes over only when a query has no procedure, the parse is unsure or the ladder is exhausted, and it stores what it did as the procedure for next time. This is the 15:30 path and the unseen-app path.
  6. Finish or 270 s guard → [C] writes the summary in the README format (respuesta: line, the reason's data on fallida, secrets scrubbed) → status terminada / fallida → the session stops acting. [F] persists anything new it learned.

4. Key decisions and the alternatives we discarded¶

Decision Chosen Discarded, and why
Screen access Raw RFB over WSS, no browser Headless browser + noVNC: adds a canvas layer, offsets that depend on resolution, slower, more to deploy (Appendix C)
Encoding Raw+CopyRect (lossless) Tight/JPEG: compression artifacts hurt OCR and pixel diffs; revisit if bandwidth hurts
Clicking Click the edge's stored last-good xy and verify the destination; replay the stored bbox while the static pixels match; a target that only moved by template match of its crop; only then the model names the target and perception grounds it Model outputs raw x,y: not accurate enough and breaks when layout shifts. OCR on every step: a second per step for nothing on a mapped app
Perception Hybrid on CPU: OCR (RapidOCR, Latin model) for text+bbox + OpenCV for widget boxes → heuristic UI tree; the model picks element ids via Set-of-Mark (Appendix H) Vision alone: imprecise boxes. OCR alone: no notion of widgets. Raw x,y from the model: fallback only. Specialist grounding models (UI-TARS, OmniParser captioner): need a GPU
Knowledge Learned per-app map, built at runtime Hand-coded SIGECOM map: zero value on the unseen app
Node identity Title band as hard key + Jaccard over static OCR labels on a coarse grid; VLM only when ambiguous (Appendix E §4.1) Pure embedding/VLM matching: ~3 MLLM calls per check. Pixel hash: breaks on any data change
Edge target Semantic target (label + role + cell) plus the last-good xy as a cache: tried first, verified by the destination, re-grounded by perception and rewritten on a miss Stored x,y alone: breaks the moment a button moves, which is exactly 15:30, with nothing to repair it. Semantic target only: perception on every replay
Initial mapping Task-driven incremental graph + ≤ 45 s menu pre-warm; traces written back after each task, so the unseen app replays from its second task. SIGECOM only: a dev-time map --visit (the same pre-warm function with a flag) and a cache seed, committed (Appendix E §4.3) Full up-front exploration at task time: 10 min to hours per app
Settle Quiet-time + expected-change check Fixed sleeps: slow and flaky
Data reads Disposable SQLite cache behind a probe: the app's change log when it has one, else the entity's grid; on a miss native export / clipboard first, OCR paging last (Appendix G) OCR every page: slow and error-prone. Always-live reads: too slow for lookups. Per-entity probe only: one route replay per entity per task
Concurrency One RFB session per task, shared=1 Exclusive session: would kick the evaluator/human viewer
Change handling Detect drift with fingerprint + action-effect checks → 4-rung localized repair, written back (§6) Full re-learn: too slow inside 5 min. Offline-only repair: fails exactly when the change hits

6. Incident response: the 15:30 change¶

Full spec in Appendix E §4.5–§6. The short version:

Signals, any one triggers: S1 target label not found · S2 no change after the action · S3 landed on a different known node · S4 landed on an unmatched screen · S5 app version string changed · S6 the edge's outcome histogram has more than one node with real mass · S7 mass drift: under 40 % of the map's menu atoms on screen at task start, or 3 unmatched screens in a row. On the data side, a changed header hash of an entity re-acquires that entity and aligns its old columns to the new ones (Appendix G §4.3.4).

Order of checks on every step: blocking dialog? → overlay? → data edge? → only then drift. Each of the first three is a cheap false-positive filter.

Repair ladder, each rung bounded, next rung only on failure:

Rung What Budget
0 Re-identify the epoch (S5 or S7 only): open a new epoch directory whose map inherits every node as stale and every edge as a hint, re-run the menu pre-warm; the old epoch is never written again. A redesign costs one pre-warm; a known epoch (the app flipped back) loads for free ≤ 10 s + pre-warm
1 Re-ground in place: template match of the old crop (moved only, no OCR) → fuzzy label → same role + cell → Jev typed choice over the element list, "which element does what the old one did", old action as few-shot, acted on at ≥ 0.8 → VLM with the Set-of-Mark image. Append the new appearance to the target, keep the node ≤ 5 s
2 Local re-explore: mark the node stale, run the pre-warm function on this node only, write the new edges ≤ 30 s
3 Re-plan with the edge marked broken: one LLM call, another graph route if one exists, otherwise free plan; rejoin the graph when a known node appears ≤ 15 s
4 Rank down, never delete: fail++, planner sees ok/fail 0

After rung 3 the tool-use loop takes the step with the planner model and writes what worked back as the procedure. Every rung logs {signal, rung, via, confidence, before, after, cost_ms} to the JSONL, which is what the Challenge 2 spec and the debrief cite.

Proving it before 15:30. Drift is a function of (stored map, live screen), so we mutate the stored map with a --mutate <kind> flag (renamed label, removed control, landing mismatch, moved menu item, unknown screen, persistent break, version bump, redesign: every atom replaced and two grid headers renamed, with and without a version bump) plus three negative controls, and assert the expected log lines. A framebuffer transform hook (0.8× downscale, +40/+25 px shift) proves nothing depends on raw x,y. Run the suite before 15:30, re-run on the real change, show the delta.

8. Assumptions and out of scope¶

  • The unseen app is a GUI with readable text (Latin script, horizontal) and conventional widgets. Canvas-heavy, drawing-style apps are out of scope.
  • No CAPTCHA or 2FA inside the remote app.
  • Destructive actions (delete, anular, Integraciones) need the task to state them explicitly. Denylist by default: Integraciones, Eliminar, Anular, Borrar, Guardar*, Enviar, Configuración.
  • "Today" is the date the app shows, not the server clock; relative dates in a task are resolved from it.
  • An ambiguous target (two customers with the same name, practice task E5) is never guessed: the task ends fallida and the summary names the candidates' ids.
  • The evaluation desktop can differ from one task to the next; nothing is tied to a URL, the map is keyed by the app's title bar.
  • One task at a time per desktop. Parallel tasks on the same desktop aren't supported.
  • VNC Authentication (type 2) only; type 1 (None) is trivial to add; VeNCrypt and RA2 are out of scope.
  • Icons with no text fall back to the VLM's raw coordinates. CPU-only deploy, no specialist grounding models.
  • The change-log probe trusts the app's own log. An edit the app does not log is caught only by the expiry backstop, or by the per-entity probe on a miss.
  • The data cache has a known staleness window (an old row edited without changing the count); bounded by an expiry time and the targeted-read path (Appendix G §4.3.1).

6. How it is evaluated¶

The evaluation set runs on another app the agent has not seen, on a clean evaluation desktop reset before each task. The desktop can change from one task to the next. Each task has 5 minutes. A task is correct when all of these hold:

  • The app has the expected changes.
  • The agent made no changes outside the task. An extra one also counts as a destructive action.
  • There are no duplicate records.
  • The final estado is the expected one. Reporting terminada on a task that didn't end well is a false success.
  • For a question, the summary carries a line respuesta: <value>. If the value is a number, the first number on that line is compared, so write it before anything else.
  • If the question asks for two values, they go on the same line, separated by ;, in the order asked: respuesta: <value 1>; <value 2>.
  • For a task that must fail, the summary names the data that explains why. If the task is a question that can't be answered, the summary has no respuesta: line.
  • A summary that repeats the desktop password or another secret makes the task incorrect.

At 5 minutes the evaluator stops polling and resets the desktop for the next task. If the agent keeps operating after that, what it does lands in the next task and counts as an out-of-task action. Stop working once you report terminada or fallida.

Rules.

  • The app may change during the day.
  • "Today" is the date the app shows; "yesterday" or "on Saturday" count from there.
  • The summary must not repeat the desktop password or other secrets the agent receives.
  • Each team member has their own desktop; what you do on yours your teammate doesn't see.
  • The agent always uses the desktop that arrives in POST /tasks. In the evaluation a different desktop arrives.

Decision: our own Python process speaks raw RFB (VNC) over WSS to the target's /websockify endpoint, using the websockets library. No browser is involved. Implementation: poc/rfb_poc.py.

Terminology. websockify is the server-side proxy the target already runs: it accepts a WebSocket and forwards the bytes over TCP to the VNC server. We didn't choose it and can't change it. On our side the client library is websockets (Python). People mix the two up, so expect the question in the debrief.

Source: Appendix B.

our process ──WSS /websockify──► websockify ──TCP──► VNC server (Docker 86a79607eef2:0) ──► SIGECOM

3.4 Layer B — VNC libraries instead of our own RFB code¶

  • asyncvnc / asyncvnc2: asyncio-based, numpy frames, clipboard support. But they connect over TCP through asyncio streams, so we'd need A4's bridge or a patched stream. They also hide FramebufferUpdate timing (our settle signal) and the choice of encoding.
  • vncdotool: Twisted-based and CLI-oriented. It's TCP-only; the noVNC maintainer confirms it can't connect to a WebSocket-only endpoint.

4. Chosen design¶

A raw RFB client in our own process (A1), in Python, on websockets, with our own protocol code. The verdict column in §3 gives the reason for each.

Why Python. The transport is the smallest part of the system. Perception (track 2), the executor and tools (track 3), and the entrypoint (track 5) all depend on Python's image and ML ecosystem. Keeping everything in one language and one process means no IPC. Raw speed doesn't matter here: the native framebuffer is 1280×800 (measured), so a full Raw frame is about 4.1 MB, incremental updates are small, and numpy slicing is far cheaper than the network. Node's one real advantage, reusing noVNC's rfb.js, is cancelled out by that code's DOM coupling.

  • Our own code: about 150 lines of protocol. We control the encodings (lossless) and see every update, so nothing hides inside the 5-minute budget.
  • Risk: the unseen app's server may use an encoding or auth type we don't handle.
  • Mitigation: we only request Raw and CopyRect, and every RFB server must support Raw. A4 stays as the fallback.

5. Trade-offs we accept (say these in the debrief)¶

  • Bandwidth. Raw is the most expensive encoding. SIGECOM's UI is mostly static, so this is fine for now. Measure it in 1.4. If it hurts, add Tight with JPEG turned off (lossless zlib) rather than JPEG.
  • We own reconnect (1.2), settle (1.3) and clipboard send (1.6). Each is a small, listed unit.
  • Auth. We support VNC auth (type 2). Adding type 1 (None) is trivial. VeNCrypt and RA2 are out of scope, and the design doc states that as an assumption.

4.1 Repair ladder for 2.6¶

Each rung is cheap, and the next one runs only if it fails. Every rung writes to the JSONL log for the Challenge 2 spec. 1. Re-ground in place. Find the same function under a new label or position (OCR fuzzy match, then the LLM with the old action as a few-shot example). If found, patch the edge and keep the node. (MobileGPT re-derive, ActionEngine Patcher, MAGNET "appearance drift".) 2. Alternative path. Search the graph for another route to the target node. (LLM-Explorer.) 3. Local re-explore. Mark the node stale and explore one hop from it, unexplored actions only, within a budget of about 20 s. (UI-KOBE frontier re-exploration, done online.) 4. Free-plan fallback. The LLM acts without the graph and rejoins it once a known fingerprint appears. (UI-KOBE.) 5. Prune. If an edge fails N times, delete it. Edges whose success has decayed are ranked down rather than deleted. (LLM-Explorer prune, MAGNET recency×use score.)

6. Evidence and measurement¶

What the literature tells us:

  1. Nobody does online remapping after an app update. - EAM and UI-KOBE name it as future work. - MAGNET handles drift only through slow memory evolution. - ActionEngine's Patcher is the closest: it localizes the failure to one node and writes the fix back into the graph. - Our 2.6 is therefore a real contribution, and the doc should say so.
  2. Exploring the whole app is too slow for us. - Every full-exploration paper spends 10 min to hours per app; MobileGPT's 10–15 min is the cheapest. - Our 5 min task budget rules out exploring the whole app first. Mapping has to be task-driven and incremental, as in MobileGPT (on demand) and AppAgentX (memory from its own runs), with only a shallow pre-warm.
  3. Identify a screen by function, not pixels. - MobileGPT (the sub-task set), LLM-Explorer (the function set), ActionEngine (static atoms) and UI-KOBE (role + layout) all strip dynamic content before comparing. - LLM-Explorer and MobileGPT both found that rules or structure beat pure LLM or vision matching for dedup.
  4. Pixels-only dedup is solved well enough. The pattern is cheap retrieval followed by a strict verify step: - UI-KOBE and PG-Agent: embedding top-k, then VLM yes/no or "reject all". - ScreenSearch: spatially binned OCR text + Jaccard ≥ 0.93.
  5. Store targets as function + label, never coordinates. - AppAgentX shortcuts store raw x,y and are fragile. - MobileGPT stores attribute-based actions (click(text:"[contact_name]")), and MAGNET stores the function plus several appearances. These survive a moved button.
  6. Plan over the graph in one LLM call, then verify each step. GraphPilot (1.03 queries/task) and ActionEngine (1.5–3.5 calls/task, 27 s) show that a graph cuts LLM calls drastically, which suits our 5 min budget.

4. Chosen design¶

4.1 Screen fingerprint (M1 → sub-problem 2.3)¶

  1. Keep static elements only: kind ∈ {title, menu, button, field label, link label, header}. Drop numbers, dates, codes (FV-#####), currency, grid body cells, and anything inside a region track 7 flags as data.
  2. Bin each kept label to a 12×8 grid on normalized coordinates → atom cell|text. Resolution-independent by construction.
  3. fingerprint = (title_band, atoms). - The title band (top ~15 %) is a hard key: it must match before anything else, so Clientes and Proveedores with identical toolbars never merge. - Then sim = Jaccard(atoms): ≥ 0.90 same node · 0.60–0.90 ambiguous · < 0.60 new node. - Ambiguous: tie-break by the inbound edge label first; only then pay for one VLM yes/no against the node's reference screenshot, with "none of them" allowed. - A node keeps one (atoms, ref_png) pair per app version (its appearances, §4.2); sim is the max over them. In a new epoch (§4.5 rung 0) the inherited stale nodes use a wider ambiguous band, 0.30–0.90, with at most 5 candidates ranked by title similarity, so a redesigned screen is re-identified as the old node (and gains an appearance) before a new node is created.
  4. Overlays are sub-states, not nodes. If changed_bbox covers < ~25 % of the screen and the parent's labels are still visible (dropdown, combo list, tooltip): overlay = parent_id + overlay labels. Close with Esc, re-verify the parent. Prevents spurious nodes, Esc edges to nowhere, and VLM calls at 0.7–0.9.
  5. Blocking dialogs are checked before drift. Small centered rectangle with ≤ 3 buttons → OCR its text into the log → Esc or the non-destructive button → re-fingerprint. A dialog never counts as drift and never starts the ladder.
  6. In-page state does not change the node. Filter text, pagination, selected row, scroll are self-loop edges with an effect field.

Done when: the same screen at two resolutions → one id; 10 distinct SIGECOM screens → 10 ids; a dropdown open/closed → same node.

4.2 Map schema (M2 → sub-problem 2.4)¶

One directory per app epoch: memory/<app_id>/<version>/ holds map.json and that version's reference PNGs and static crops, named by node id (epoch-<n> when the title bar carries no version). No database. The live epoch is the directory named after the title bar's version; once a newer one exists the old directory is never written again, which is what makes it a frozen version. §4.5 rung 0 says when a new one is opened.

node      = {id, title, description, transient, stale, seen, last_seen,
             appearances: [{version, atoms[], ref_png, elements_snapshot, last_seen}]}   // one per app version, newest first; crops as files
edge      = {from, action: {kind, target: {appearances: [{version, label, role, cell, xy}]}, params},
             to, effect, data?, scroll?, inherited?, ok, fail, last_ok, outcomes: {node_id: count}}
procedure = {task_text, steps: [edge_id | self_loop + params], ok, last_ok}
unexplored[node_id] = [action signatures not yet tried]       // the frontier
denylist  = ["Integraciones", "Eliminar", "Anular", "Borrar", "Guardar*", "Enviar", "Configuración"]
  • description is written by the LLM lazily, in one batched call at write-back, never per node.
  • appearances is MAGNET's "function → many appearances" (§3.1 idea 9): the node id and its description are the stable function; each app version adds a look: its atoms, ref_png, elements_snapshot and the static crops the replay fast path compares, stored as files in that version's directory. Fingerprint matching and target grounding take the newest appearance first and fall back through the older ones. Rung 1 appends an appearance; it never overwrites one.
  • xy on a target appearance is the last click point that worked: a cache, never the identity. Replay (Spec W replay_edge) checks the crop around it byte-for-byte before clicking, clicks it or its template-matched position, verifies the landing against to, and on a miss perceives, grounds label + role + cell, clicks and overwrites xy (logged fastpath: repaired).
  • Static crops are the title-band app-title element plus every menu, button, field-label and header bbox padded 2 px, cut from ref_png; grid bodies and values are excluded, so a filter, a page change or a selected row still replays. Byte equality of these crops is the gate for "same node, nothing moved".
  • inherited: true marks an edge copied from the previous epoch and not yet verified in this one. The planner sees it as a hint, ranked below any verified edge; the first confirmed landing clears the flag.
  • data: true when the target is not in the static set (a grid row, a record code). A miss on a data edge runs the find procedure (search field → type → Enter → Siguiente ≤ N pages), never the repair ladder. We store the procedure, not the row click.
  • scroll: true when the target was only found after one PageDown. "Not found" is declared only after that re-OCR.
  • outcomes is the histogram of where this action actually led. More than one node with real mass = an unreliable edge (S6).
  • Edge rank = ok / (ok + fail) × recency decay. The planner sees edges with their ok/fail; nothing is deleted (see §4.5, rung 4).
  • Denylist labels are never clicked unless the task names them.

Done when: a second task on the same app loads the map and finishes faster than the first.

4.3 Initial mapping (M3 → sub-problems 2.2 and 2.5)¶

Decision for 2.5: cold + incremental, with one bounded pre-warm. No app-wide exploration ever.

  1. Connect → identify app → load the epoch or start cold. ~5 s. (app_id, version) matches a frozen epoch (the app flipped back): load it. Same app_id, new version: §4.5 rung 0 (inherit, pre-warm). No app_id at all (the title bar was rebranded): Jaccard of the first screen's menu atoms against every stored app's root node; ≥ 0.5 adopts that app as a new epoch, else cold.
  2. Pre-warm, first task on an epoch only, ≤ 45 s. Open each top menu: click → settle → OCR → Esc ≈ 4 s × ≤ 8 menus. Menus whose label matches a task keyword go first. Open menus only, never click items. Record menu → item edges with to = unknown. Skip entirely when the first screen already shows a task keyword. Denylist applied. Result: the planner sees the whole menu tree without visiting a single screen.
  3. Task-driven mapping. Every action during a task: act → settle → elements → fingerprint → create/match node → upsert edge with the observed to. An edge is persisted only once its landing fingerprint is confirmed. Nothing is learned off the task path unless the planner is stuck.
  4. Frontier mode (planner stuck). Take the unexplored actions on the current node, ranked by label similarity to the task text; one action per step; back out via Esc or the recorded return edge. ≤ 40 s per episode.
  5. Write-back at task end. Nodes (with a refreshed elements_snapshot and static crops on the current version's appearance), edges and the procedure persisted; new nodes described in one batched LLM call. So the unseen app replays from its second task.
  6. Dev-time full mapping (map --visit, SIGECOM only). The same pre-warm function with a visit flag also clicks every non-denylisted menu item, settles, perceives, saves the node's appearance with snapshot, ref_png and crops plus the confirmed edge with the xy it clicked, and returns via Esc or the recorded back edge (budget 10 min). It then seeds the read cache from every node with a grid (Appendix G §4.2 step 4). The result is committed in memory/ and shipped in the image; the unseen app never gets this run and learns through steps 1–5.
  7. lazy: background frontier exploration between tasks, only if a spare session exists. Shared session risk: operador/operador2 collisions.

Done when: the first task on SIGECOM records the 9 menu screens as edges within the 45 s pre-warm, with no hand-written coordinates.

4.4 Task-time use (M4 → feeds 3.5)¶

  1. Plan. On a mapped app the plan is the parsed queries plus the stored procedure for each (op, entity) (Appendix F §4.1); the graph planner call below runs only in the fallback loop and at §4.5 rung 3. Input: task + compact graph (node titles + descriptions; edges as Inicio —[click "Cartera › Facturas"]→ Facturas; procedures whose task_text is similar). Output: ordered steps, each an edge, a self-loop with params, or explore.
  2. Execute a step. Cheapest grounding first: the stored bbox while the node's static crops match byte-for-byte (Spec W observe); a target that only moved, by template match of its stored crop over the frame (≥ 0.95, logged fastpath: moved); only then perception: ground target.label on the current elements (exact → fuzzy → same role in the same cell). Then act → settle → fingerprint → compare with edge.to. Match: ok++, next step. Mismatch: §4.5. - fill_field: click the paired input box (7.3), confirm a caret or text appeared inside that bbox, else Tab. Keyboard focus is invisible to the fingerprint.
  3. Verify completion against the last screen's elements; write the summary in the README format.
  4. Targets per step: act + settle ≤ 2 s, OCR ≤ 1 s when it runs, fingerprint in ms. LLM calls per task: 2 on a warm map (parse, summary), ≤ 3 with one replan.

4.5 Change detection and repair (M5 → sub-problem 2.6, the 15:30 path)¶

Signals (any one triggers):

Signal
S1 target label not found on the screen
S2 no change after the action (changed_bbox is None, or the same fingerprint on a non-self-loop edge)
S3 landed on a different known node
S4 landed on an unmatched screen
S5 app version string changed
S6 the edge's outcomes histogram has > 1 node with real mass
S7 mass drift: at task start fewer than 40 % of the map's menu atoms are on screen, or 3 consecutive S4 inside one task (threshold tunable)

Order of checks on every step: blocker dialog? → overlay? → data edge? → only then drift. Each of the first three is a cheap false-positive filter.

Ladder — four rungs, each bounded, next rung only on failure. Every rung logs {signal, rung, via, confidence, before, after, cost_ms} to the JSONL (this is the evidence the Challenge 2 spec cites).

Rung What Budget When it fires
0 Re-identify the epoch. Open memory/<app_id>/<new version>/ with a map.json copied from the previous epoch, every node stale and every edge inherited; appearances keep their version, so their crops and ref_png still resolve into the old directory; run the §4.3 step 2 pre-warm again. From here each inherited edge goes through rungs 1–3 with its old appearance as the few-shot, and unmatched screens are re-identified against inherited nodes before becoming new ones (§4.1). ≤ 10 s + one pre-warm S5 or S7 only: a version bump or a redesign.
1 Re-ground in place. Template match of the old crop (moved only, no OCR) → fuzzy label → same role + cell → Jev typed choice over the element list, "which element does what the old one did", with the old action as a few-shot example, acted on at confidence ≥ 0.8 → VLM with the Set-of-Mark image. Append the new look to target.appearances, keep the node. ≤ 5 s Most of 15:30: a renamed label, a moved item, a new field or confirm dialog.
2 Local re-explore. Mark the node stale, run §4.3 step 4 on this node only, write the new edges. It is the pre-warm function applied to one node: no new code. ≤ 30 s An item moved to another menu.
3 Re-plan with the edge marked broken. One LLM call: the planner takes another graph route if one exists, otherwise plans freely. Every step still fingerprints, so the moment a known node appears we rejoin the graph. ≤ 15 s Workflow drift.
4 Rank down, never delete. fail++; the planner prompt shows the edge with its ok/fail. 0 Always, after any failure.

Entry rung depends on the signal: S5/S7 → 0, then every inherited edge follows S1 → 1 → 2 → 3. S1 → 1 → 2 → 3. S3/S4 → Esc/back to the previous node (2 s) → 3. After rung 3 the tool-use loop takes the step (Appendix F §4.1) and writes what worked back as the procedure.

Why rung 0 exists: without it a redesign is discovered one edge at a time, at up to 50 s per edge, and the budget is gone after three. Recognising the epoch once turns it into a first task on a new app with the old map as hints: one pre-warm, and the old version stays loadable for a flip-back and for the before/after diff in the debrief.

Why four and not five: a task-driven graph of 10–20 nodes almost never has an alternative route, so the papers' "alternative path" rung would not fire; it is folded into rung 3. Deletion risks losing a good edge to three unlucky failures, so pruning is replaced by ranking. lazy: add pruning when the map grows past what fits in the prompt.

1. Summary¶

Decision: the loop runs in-process with plain Python tool functions, with no MCP, and every model call goes through OpenRouter (openai SDK with base_url; the Anthropic SDK is not used). The order on every task, each layer earning its place on the 3.6 harness: 1. Parse. One fast-model call turns the natural-language CRUD action into typed queries (op, entity, where, fields, aggregate). 2. Execute (L3). A deterministic executor answers reads from the cache behind the change-log probe (Appendix G §4.2) and replays stored procedures for writes, clicking stored positions while the pixels match (Appendix E §4.4). No further model call and no OCR on a mapped app. 3. System 1 on a changed screen (L4). Jev answers the typed per-step questions (which element is the target now, did the action work, is this drift) with a calibrated probability; below the gate, the VLM; still unsure, rungs 2–3 of the ladder. 4. Fallback (L1+L2). The tool-use loop with batched actions runs only when a query has no stored procedure (the first task on an unseen app), the parse is unsure, or the ladder is exhausted, and it writes the steps that worked back as the procedure.

Terminology. System 2 is the slow, deliberate planner (the planner model, through OpenRouter). System 1 is a fast decision function that answers narrow, typed questions in about 100 ms (Jev). Jev is TypeSafe AI's "System One" model. It does not generate text: it returns typed choices or scores, each with a calibrated probability.

4. Chosen design¶

4.1 Recommendation and order¶

  1. Parse. One MODEL_FAST call turns the natural-language CRUD action into typed queries (op ∈ {read, create, update, delete, explore}, entity, where, fields, aggregate, key), given the cache entities with their columns and the stored (op, entity) procedures, so "facturas vencidas" maps to the Facturas node id with where {Estado: Vencida}; confidence under 0.8, or an (op, entity) with no stored procedure, hands the task to step 4.
  2. L3. The executor: reads behind the change-log probe (Appendix G §4.2), writes by replaying the stored procedure, stored positions while the pixels match (Appendix E §4.4), strict checks per step. No OCR and no further model call on a mapped app.
  3. L4. On a replay miss, Jev answers target, effect_ok and drift in one call; below the gate the VLM with a Set-of-Mark image; then rungs 2–3 of the ladder (Appendix E §4.5).
  4. L1+L2. The tool-use loop with batched actions (max 8 tool calls per batch, stopped at the first failed Effect), on MODEL_PLANNER: the last rung, and the first task on an unseen app. It writes the steps that worked back as the procedure, so the next task runs through step 2.
  5. Throughout, apply the accelerators from §4.2.

4.2 Cross-cutting accelerators (apply to every option)¶

  • Text over images. Send the OCR element list by default. Send a screenshot (or a crop) only when the model asks or a check is ambiguous.
  • Prompt caching on the system prompt, the tool schemas and the app map summary. Steps after the first pay only for the changing state.
  • Model tiering. Three OpenRouter tiers from env: MODEL_FAST (parse, summary, Jev's keyless fallback), MODEL_VLM (image questions), MODEL_PLANNER (fallback loop, replan). Tune the ids on the harness, never in code; the Anthropic SDK is not used anywhere.
  • App Memory shortcuts. go_to(screen) replaces about 5 menu clicks with one step (see Appendix D and Appendix E §4.4).
  • Settle. Quiet-time plus an expected-change check, never fixed sleeps. With L4 this becomes the dominant cost.

4.3 Jev as System 1 (L4)¶

Fit. Our perception already turns the screen into text (elements with label, kind and bbox). That is exactly the kind of input Jev takes. The per-step decisions in L3 are narrow classifications, which is Jev's sweet spot. Planning, writing field values, the final summary and anything numeric stay in the OpenRouter models or in code.

5. Trade-offs¶

What the harness must show for Jev, compared to the keyless MODEL_FAST fallback and to the VLM-only ladder: - success % no more than 5 points lower; - at least 5× faster per decision; - escalation rate under 30%.

If it fails, decide points at MODEL_FAST and nothing else changes: Jev only answers the per-step questions; the executor and the fallback loop stay intact.

7. Open questions¶

Risks of Jev as System 1. 1. Access. Key in hand. If it stops working, decide falls back to MODEL_FAST and nothing else changes. 2. Out-of-distribution behaviour. The evaluation app is unseen. The confidence gate is the mitigation. 3. Unverified claims. The vendor states 40–200× speedups; users report a median of about 7×. 4. Wrong-but-valid answers. Jev can't produce an invalid type, but it can choose the wrong element. The effect_ok check after each action catches this. 5. Model ids. The three OpenRouter tiers are placeholders in .env.example until filled by hand; the fakes keep the tests independent of them.

1. Summary¶

Scope: an expansion of solution.md §5 Track 4 (4.1–4.4). Decision: a one-way pull from the screen into a disposable SQLite read cache. Freshness is checked with a probe, cheapest scope first: the app's own change log when it has one (SIGECOM: Herramientas › Bitácora de cambios, one screen for every entity), else the entity's grid. The app always wins, and write tasks never read from the cache.

2. Problem and constraints¶

What "sync" means here. There is no API, no change feed and no second database to reconcile with. The only source is pixels coming over RFB (Appendix B). In this project, "sync" means:

 Remote app (source of truth)  ──pixels / clipboard / export──►  Agent cache (SQLite)  ──►  task answer
          ▲                                                              │
          └───────────── writes happen ONLY through the UI ◄─────────────┘ (cache is never pushed back)
  • Direction: one way. Data only flows from the app into the cache.
  • Who wins: the app, always. The cache is a read copy that can be thrown away. Deleting the file loses nothing except speed.
  • Why it exists: read tasks such as lookups, filters and counts have to finish well inside the 5-minute budget. The target is a lookup in under 30 s (4.3). Walking and OCR-ing a grid on every task is too slow and too error-prone.
  • What it is not: it is not the app map. Screens, paths and procedures stay in the per-app JSON from Appendix E §4.2. This page covers business data only (Clientes, Facturas, Pedidos, or whatever entities the unseen app has).

The steps: 1. The agent asks for an entity, not for a screen. The sync engine keeps moving between screens and reading out of the LLM's context. 2. Cache hit + probe matches: answer from SQL. Cost: one route replay to the change log per task (or one per entity when the app has no change log) plus one first-page read, a few seconds. 3. Miss or mismatch: acquire the data through the ladder, cheapest and most reliable method first. Each step either returns complete rows or hands off to the next. - Export (4.1): the whole table in one action. Lossless if the file or screen it produces can be read. - Clipboard (4.4): select-all + copy → ServerCutText. Lossless text, usually tab-separated. - OCR paging (4.2): read a page, press Siguiente, repeat. Always available, but it is the slowest and least accurate. 4. Normalise: match columns by header text, never by position. Parse types (dates, money, ints). Compute the natural key and row_hash. 5. Write everything to a staging table. Only a complete read is swapped in, in one transaction. Readers never see half a table. 6. Record sync_state (count, probe hash, header hash, method, time). Log every step to the JSONL log [H].

4.1.2 Read task, one record (targeted path)¶

When the task names a single record ("total of factura F-0042"), do not sync the whole table. Use the app's own search or filter field instead, read the one row, and upsert it into the cache with source = targeted. This takes seconds instead of minutes and usually beats a cold full sync.

4.2 Keeping it in sync¶

Nothing pushes changes to us. Freshness has to be detected by looking at the screen. In order of use:

  1. Our own writes → write-through read-back. After the agent saves a record through the UI, it reads that record back off the screen and upserts just that row. This upgrades the original "invalidate after any write" (4.3) because it keeps the rest of the table warm. Then re-read change-log page 1 so the watermark includes our own entry; that entry is also the proof of the write for the summary. If the read-back fails, fall back to marking the whole entity stale.
  2. Probe before trusting the cache. A probe is the cheapest signal that "something changed", cheapest scope first: - The app's change log, when it has one (SIGECOM: Herramientas › Bitácora de cambios). It is registered as an entity with role = 'changelog' and probed once per task: its page-1 hash equals the stored watermark → every entity is fresh, no per-entity route replay. It differs → every entity is marked stale, re-acquired lazily only when a query needs it, and the watermark advances. v1 marks everything; naming the touched entity from the row waits until the screen's columns are known (§7). An app with no change log skips this scope. - The entity's own grid: the total count (footer, "Mostrando 1-20 de 812", or the page count × page size) and a hash of page 1, sorted newest first if the grid can sort. Together these catch inserts, deletes and edits to recent records. A probe costs one route replay plus one OCR region.
  3. Expiry time as a backstop. Even if the probe matches, a snapshot older than N minutes (start with 10 and tune it) is re-acquired the next time it's needed. This bounds the blind spot described in §4.3.1.
  4. Dev-time seed (SIGECOM only). After map --visit (Appendix E §4.3 step 6), seed finds every mapped node whose snapshot has a grid, registers it as an entity (keyed by the node id, header hash from its columns) and acquires it through the §4.4 ladder into memory/cache.sqlite; the node whose title matches bitácora|cambios|log|historial|auditor is registered with role = 'changelog' (a fast-model tie-break when several or none match). The file is committed, so a lookup right after deploy hits the cache; a stale seed costs one re-acquire, never a wrong answer, because the probe runs first. Never seed inside a task, and never on the unseen app: there, entities are acquired lazily the first time a query needs them, and the in-task pre-warm stays menus only.

4.3 What if something changes before or during a sync?¶

Who can change data behind our back: - another operator on the same desktop: shared=1, operador and operador2 (1.5) - the evaluator setting up test data between tasks - the 15:30 change: this one changes the UI or structure, not just the data

4.3.1 External edit after our snapshot¶
Change Caught by Result
Row inserted or deleted Probe count Re-acquire
Recent row edited Probe page-1 hash (newest first) Re-acquire
Old row edited, count unchanged Not caught by the probe Served stale until the expiry time or a targeted read

The last row is the known staleness window, and we accept it. When the app has a change log that records edits, the change-log probe closes it: an old-row edit is a new log entry. Mitigations when it has none: - the expiry time puts an upper bound on it - any answer that depends on one specific record goes through the targeted path (§4.1.2), which always reads live - the task summary states when an answer came from the cache and how old that cache was

4.3.2 Edit while we are paging¶

Paging is not a snapshot. An insert shifts rows down, which makes a row appear twice. A delete shifts rows up, which makes one get skipped.

  • Remove duplicates by natural key while staging.
  • Probe at the start and at the end. If the count or page-1 hash changed during the read, discard the staging table and retry once.
  • If it changes a second time, the table is "hot". Don't swap it in. Mark the entity stale and answer through the targeted path or live reading.
  • Export and clipboard are near-atomic (one action), so this risk exists almost entirely on the OCR-paging step. That is another reason the ladder puts them first.
4.3.3 Write tasks never trust the cache¶

Before the agent edits or creates anything: 1. Read before write: open the actual record on screen. 2. Check expectations: if the task implies a current state ("change the status of the pending order X"), confirm that state on screen. This is optimistic concurrency done by hand. The screen is the version check. 3. If it doesn't match, don't overwrite. Report the conflict in the summary ("expected pending, found shipped by another user") and end as fallida or partial. Never guess. 4. Save → read back → verify the new values are on screen → write-through to the cache (§4.2, step 1).

Two agents editing the same record at the same time is ruled out by the assumption "one task at a time per desktop" (solution.md §8). A human operador2 is not ruled out, and steps 2 and 4 are what protect us from them.

4.3.4 Schema or UI drift (the 15:30 change)¶
  • Each entity stores a header hash (its sorted column labels). If a column is renamed, added or removed, the hash changes. When it does, re-acquire the entity's rows (they are disposable, so re-acquire is the migration) and then align the old headers to the new ones, cheapest rung first: 1. normalised exact match (case, accents, whitespace, punctuation); 2. difflib.SequenceMatcher ratio ≥ 0.8 (stdlib); 3. value match: join old rows to new rows on the natural key, when the key column aligned in 1–2, and pair the columns whose parsed values agree on ≥ 90 % of the shared keys; 4. leftovers: one LLM call with the old headers, the new headers and 3 sample rows, "no counterpart" allowed.
  • The result is sync_state.column_map, {"old header": "new header"}, chained across epochs so the oldest name stays usable. data_json is always keyed by the live header; a query written against an older name is translated through the map. This is what keeps learned procedures and the planner's "Valor is the amount" valid across a rename. Headers with no counterpart are left out of the map and logged (sync.schema_drift {old, new, aligned, unaligned}). If the alignment is inconclusive, the behaviour is the old one: an empty entity, no map.
  • Columns are mapped by header text, so a column that only moves doesn't break anything.
  • The entity key is the app map's node id for the grid screen, not the screen title; the title is one of that node's appearances (Appendix E §4.2). A renamed screen is still the same entity. The sync engine stores the id it is given and never reads the map itself.
  • If a screen or grid can't be found, that's the app map's job: drift detection (2.6) and the repair ladder in Appendix E §4.5. The sync engine marks the entity stale and waits for the app map to repair.
4.3.5 Conflict policy, in one line¶

The app always wins. We do no merging and no last-write-wins on our side, and the cache never overwrites the app.

1. Summary¶

Decision: a hybrid, CPU-only pipeline. - OCR (RapidOCR with a Latin model) gives exact text and boxes. - Classic CV (OpenCV) gives widget boxes: fields, buttons, grid lines. - Heuristics turn those into a UI tree: containment, grouping, label↔field pairing, grids. - The model (the planner or the VLM, through OpenRouter) sees an element list, plus a Set-of-Mark image only when the screen is new, and answers with an element id, never x,y. On a mapped app it is not asked at all: the saved snapshot replays first (Spec W). - Raw coordinates from the VLM are a last-resort fallback.

The whole pipeline is built around caching, because measurement (§6) shows that recognizing every line is the expensive part, not finding them.

2. Problem and constraints¶

framebuffer (numpy, 1280×800, lossless)
   → elements  [{id, text, bbox, kind, conf}]          kind: menu, button, field, label, link, cell, title
   → UI tree   (window → panels → forms/grids → widgets)
   → used by:  grounding (3.2) · fingerprint (2.3) · app map (2.4) · drift detection (2.6) · read_grid (4.2)

There's no DOM and no accessibility tree; the transport only gives us pixels (Appendix C). Perception rebuilds the accessibility tree a normal app would expose. That's exactly the problem Apple's Screen Recognition paper solves for mobile apps.

What makes our case easier than the papers: - Pixels are lossless (Raw encoding): no JPEG noise. Identical text renders to identical pixels, which makes caching exact. - Fonts are fixed and the UI is flat, light-themed and web-styled, with standard widgets (see poc/out/before.png). - Text is Spanish/Latin script, printed horizontally.

What makes it harder: - The evaluation app is unseen, so there's no training or labels for it. - The deploy is CPU-only (Railway). - 5 minutes per task, and the UI changes at 15:30.

3.4 Building the tree — the two routes in the literature¶

The literature takes two routes: - Learned end-to-end: a model outputs the structure directly. pix2code (2017) produces a DSL; Pix2Struct (2022) parses screenshots into simplified HTML; ScreenAI (2024) produces a "screen schema" of type + box + text. These need training data and a GPU. - Detect, then group with heuristics: REMAUI (2015) uses OCR + CV and then merges into a view hierarchy; UIED (2020) is a hybrid detector; Xie et al. (2022) add Gestalt grouping; Apple's Screen Recognition (2021) uses a detector + grouping + reading order to produce an accessibility tree.

4. Chosen design¶

4.1 Building the tree: detect, then group with heuristics¶

We take the second route, because it works on an unseen app with no training. The steps: 1. Containment. If box A lies inside box B, A is B's child. That gives window → panel/dialog → widgets. 2. Perceptual grouping (Gestalt, Xie 2022). Widgets that are aligned, close together and similarly styled become one group: a menu bar, a filter row, a form, a toolbar. 3. Label ↔ field pairing. An input box takes as its label the nearest text above or to the left of it. On SIGECOM, "Cliente" sits above the text box and "Estado" above the select. That's what makes fill_field("Cliente", "Ruiz") possible. 4. Grids. A header row of text aligned with columns of repeated rows becomes a table with named columns. On SIGECOM that's Código, Cliente, Fecha, Vence, Valor, Estado. That feeds read_grid() (4.2). 5. Kind classification by rules: - Text inside a bordered box with a fill → button. - Empty bordered box → field. - Bordered box with ▾ → select. - Blue underlined text → link. - Text in the top band → menu. - Text in the header row → column header.

Above the tree: the app map. The literature treats each screen tree as a node and each action as an edge: - GUI Ripping (Memon 2003) builds a "GUI forest" plus an event-flow graph. - DroidBot (2017) builds a UI transition graph. - AppAgent (2023) has an LLM explore the app and write per-app docs.

That's our tracks 2.2 and 2.4. Perception only has to deliver a stable tree and fingerprint for each node.

4.2 Fingerprint and change detection¶

  • Fingerprint: the sorted set of stable texts (title, menu, labels, column headers), plus a coarse layout hash of the tree. Values are excluded: grid cells, dates, the "Hoy:" clock. It doesn't depend on resolution, because it uses text and relative structure, not pixels.
  • Moved, not changed: before any OCR, a static element whose crop no longer matches at its stored bbox is searched over the frame with cv2.matchTemplate; lossless frames make the match exact, so a hit at ≥ 0.95 updates the bbox and skips perception (Spec W). Only a crop found nowhere triggers OCR.
  • Drift (15:30):
  • Same fingerprint but a known element is missing or has moved means a changed screen.
  • An unknown fingerprint after a known action means a changed route.
  • Either way, it's reported to 2.6.

4.3 Recommended pipeline¶

action → settle → changed_bbox (poc/rfb_poc.py:149)
              │
              ▼
  ┌── text DETECTION on changed region (or full screen if new) ── ~0.7 s full screen
  │      each line box → hash its pixels → line cache hit? ── yes → text (≈0 ms)
  │                                                    └── no → RECOGNITION (~50 ms/line) → cache
  ├── CV boxes (OpenCV contours + grid lines) ── ms
  ▼
merge → elements → tree (containment · grouping · label↔field · grids · kinds)
  │
  ├─► fingerprint → screen cache: known screen = reuse whole tree, re-read only changed region
  ├─► app map (2.4) / drift (2.6)
  └─► the model: element list as text; + SoM image only on new or unexpected screens
fallbacks: conf < 0.8 → flagged (upscale + Tesseract deferred) · no text/no box → VLM raw x,y

Two caches make this fast: - Line cache: key = hash of the line's pixels, value = text. Because frames are lossless and fonts are fixed, the same label always renders to the same bytes. - Screen cache: key = fingerprint, value = tree. It also lets lazy grid reading work: recognize only the columns or rows the task asks about.

5. Trade-offs we accept¶

  • Icons with no text aren't understood. They fall back to the VLM's raw coordinates, or to the optional detector.
  • Heuristic grouping can mis-pair labels on dense forms. Action verification (3.3) catches it: "typed into a field, the wrong area changed."
  • CPU only: no specialist grounding models and no learned tree models. They're next steps if we get a GPU.
  • Latin-script, horizontal text is an assumption already stated in the design.

"""POC: talk RFB (VNC) straight to noVNC's /websockify — no browser.

  uv run poc/rfb_poc.py probe          # connect, print ServerInit + timings, save screen.png (no input sent)
  uv run poc/rfb_poc.py click X Y      # click, wait until settled, save before/after

  uv run poc/rfb_poc.py mcp            # stdio MCP server: screenshot / click / type_text / key
"""
import asyncio
import io
import struct
import sys
import time
from pathlib import Path

import numpy as np
from Crypto.Cipher import DES
from PIL import Image as PILImage
from websockets.asyncio.client import connect

ROOT = Path(__file__).resolve().parent.parent
OUT = Path(__file__).resolve().parent / "out"
KEYS = {"enter": 0xFF0D, "tab": 0xFF09, "backspace": 0xFF08, "esc": 0xFF1B,
        "up": 0xFF52, "down": 0xFF54, "left": 0xFF51, "right": 0xFF53}


def log(*a):
    print(*a, file=sys.stderr, flush=True)  # stdout belongs to MCP in mcp mode


def env():
    return dict(l.split("=", 1) for l in (ROOT / ".env").read_text().splitlines() if "=" in l)


class RFB:
    def __init__(self):
        self.buf = bytearray()
        self.last_change = 0.0
        self.clipboard = ""
        self.updated = asyncio.Event()

    async def _read(self, n):
        while len(self.buf) < n:
            self.buf += await self.ws.recv()
        out, self.buf = bytes(self.buf[:n]), self.buf[n:]
        return out

    async def connect(self):
        e = env()
        url = e["URL"].replace("https://", "wss://").rstrip("/") + "/websockify"
        t0 = time.perf_counter()
        self.ws = await connect(url, subprotocols=["binary"], max_size=None)
        ver = await self._read(12)
        await self.ws.send(b"RFB 003.008\n")
        n = (await self._read(1))[0]
        types = await self._read(n)
        if 2 not in types:
            raise RuntimeError(f"no VNC auth offered: {list(types)}")
        await self.ws.send(b"\x02")
        challenge = await self._read(16)
        # VNC auth quirk: DES key is the password with each byte's bits reversed
        key = bytes(int(f"{b:08b}"[::-1], 2) for b in e["PASSWORD"].encode()[:8].ljust(8, b"\0"))
        await self.ws.send(DES.new(key, DES.MODE_ECB).encrypt(challenge))
        if struct.unpack(">I", await self._read(4))[0] != 0:
            raise RuntimeError("VNC auth failed")
        await self.ws.send(b"\x01")  # ClientInit shared=1: don't kick other viewers
        self.w, self.h = struct.unpack(">HH", await self._read(4))
        await self._read(16)  # server pixel format, overridden below
        self.name = (await self._read(struct.unpack(">I", await self._read(4))[0])).decode(errors="replace")
        self.t_handshake = time.perf_counter() - t0
        self.server_version = ver.decode().strip()

        # 32bpp little-endian true colour -> bytes arrive as B,G,R,X
        await self.ws.send(b"\x00\0\0\0" + struct.pack(">BBBBHHHBBB3x", 32, 24, 0, 1, 255, 255, 255, 16, 8, 0))
        await self.ws.send(struct.pack(">BxHii", 2, 2, 0, 1))  # SetEncodings: Raw, CopyRect (lossless only)
        self.fb = np.zeros((self.h, self.w, 4), np.uint8)
        self.reader = asyncio.create_task(self._loop())
        await self._request(incremental=False)
        await self.updated.wait()
        self.t_first_frame = time.perf_counter() - t0

    async def _request(self, incremental=True):
        await self.ws.send(struct.pack(">BBHHHH", 3, int(incremental), 0, 0, self.w, self.h))

    async def _loop(self):
        while True:
            msg = (await self._read(1))[0]
            if msg == 0:  # FramebufferUpdate
                (n,) = struct.unpack(">xH", await self._read(3))
                for _ in range(n):
                    x, y, w, h, enc = struct.unpack(">HHHHi", await self._read(12))
                    if enc == 0:
                        self.fb[y:y + h, x:x + w] = np.frombuffer(await self._read(w * h * 4), np.uint8).reshape(h, w, 4)
                    elif enc == 1:
                        sx, sy = struct.unpack(">HH", await self._read(4))
                        self.fb[y:y + h, x:x + w] = self.fb[sy:sy + h, sx:sx + w].copy()
                    else:
                        raise RuntimeError(f"unexpected encoding {enc}")
                if n:
                    self.last_change = time.perf_counter()
                self.updated.set()
                await self._request()  # keep a request outstanding, like noVNC does
            elif msg == 1:  # SetColourMapEntries
                _, cnt = struct.unpack(">xHH", await self._read(5))
                await self._read(cnt * 6)
            elif msg == 2:  # Bell
                pass
            elif msg == 3:  # ServerCutText
                (ln,) = struct.unpack(">3xI", await self._read(7))
                self.clipboard = (await self._read(ln)).decode("latin-1")
            else:
                raise RuntimeError(f"unknown server message {msg}")

    # lazy: quiet-time only; SIGECOM paints in two phases (>300ms gap). Real fix = verify a per-screen anchor.
    async def settle(self, quiet=1.0, timeout=8.0):
        """Return once no screen changes arrived for `quiet` seconds. No fixed sleeps per action."""
        start = time.perf_counter()
        await asyncio.sleep(quiet)
        while time.perf_counter() - self.last_change < quiet and time.perf_counter() - start < timeout:
            await asyncio.sleep(0.05)
        return time.perf_counter() - start

    async def click(self, x, y):
        await self.ws.send(struct.pack(">BBHH", 5, 0, x, y))
        await self.ws.send(struct.pack(">BBHH", 5, 1, x, y))
        await self.ws.send(struct.pack(">BBHH", 5, 0, x, y))

    async def key(self, keysym):
        await self.ws.send(struct.pack(">BBxxI", 4, 1, keysym))
        await self.ws.send(struct.pack(">BBxxI", 4, 0, keysym))

    async def type(self, text):
        for c in text:  # Latin-1 chars (ñ, á...) map 1:1 to keysyms
            await self.key(KEYS["enter"] if c == "\n" else ord(c))

    def png(self, path=None):
        img = PILImage.fromarray(self.fb[:, :, 2::-1])  # BGRX -> RGB
        if path:
            path.parent.mkdir(exist_ok=True)
            img.save(path)
        b = io.BytesIO()
        img.save(b, "PNG")
        return b.getvalue()


def changed_bbox(a, b):
    ys, xs = np.nonzero((a != b).any(axis=2))
    return None if not len(xs) else (int(xs.min()), int(ys.min()), int(xs.max()), int(ys.max()))

    before = r.fb.copy()
    if cmd == "probe":
        log(f"saved {OUT / 'before.png'}")
        return
    t0 = time.perf_counter()
    if cmd == "click":

def mcp_server():
    from mcp.server.fastmcp import FastMCP, Image

    app = FastMCP("sigecom-poc")
    conn = {}

    async def rfb():
        if "r" not in conn:
            conn["r"] = RFB()
            await conn["r"].connect()
        return conn["r"]

    async def shot():
        r = await rfb()
        await r.settle()
        return Image(data=r.png(), format="png")

    @app.tool()
    async def screenshot() -> Image:
        """Screenshot of the SIGECOM legacy app (VNC desktop). Coordinates are image pixels."""
        return await shot()

    @app.tool()
    async def click(x: int, y: int) -> Image:
        """Left-click at pixel (x, y), wait until the screen settles, return the new screenshot.
        Never open Herramientas > Configuración > Integraciones."""
        await (await rfb()).click(x, y)
        return await shot()

    @app.tool()
    async def type_text(text: str) -> Image:
        """Type text into the focused field (use \\n for Enter), then return the new screenshot."""
        await (await rfb()).type(text)
        return await shot()

    @app.tool()
    async def key(name: str) -> Image:
        """Press a special key: enter, tab, backspace, esc, up, down, left, right."""
        await (await rfb()).key(KEYS[name])
        return await shot()

    app.run()


if __name__ == "__main__":
    if sys.argv[1] == "mcp":
        mcp_server()
