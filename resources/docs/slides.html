A distributor runs customers, orders and invoices in a system only its screen can reach. The evaluator sends a task in Spanish plus a desktop URL and password, and polls for the result.

04 / THE BET

SPEAK RFB. LEARN WHILE RUNNING. REPLAY WHAT YOU LEARNED.

01

OUR OWN RFB CLIENT

Raw RFB 3.8 over WebSocket, no browser: lossless frames, shared session, a dropped socket heals itself, key chords like ctrl+a arrive as one press.

02

PERCEIVE ONLY ON CHANGE

OCR and classic CV on CPU run only when the pixels changed. A screen the map already knows is replayed from stored positions, byte for byte.

03

THE TOOL LOOP LAST

A model drives clicks only when there is nothing to replay, and what it did is stored as the procedure for next time. The first task learns; the second replays.

07 / PERCEPTION

OCR ONLY WHEN SOMETHING CHANGED

RAPIDOCR + OPENCV

A TYPED TREE, ON CPU

Text lines from RapidOCR, widget boxes from OpenCV, paired into fields, buttons, menus, grid cells. No GPU, no grounding model.

INCREMENTAL

RE-READ THE CHANGED BOX ONLY

Line images are cached by hash; after a click only the region that changed is OCR'd. A known screen is served from its stored snapshot.

GROUNDING

EXACT → FUZZY → CELL

The model names an element; the tool resolves it: exact label, fuzzy ≥ 0.8, then the only element of that role in the grid cell. Never raw x,y.

RAILWAY

4 THREADS, LAPTOP SPEED

The container sees 48 CPUs; uncapped, OCR spawned a thread per CPU. OMP_NUM_THREADS=4 in the image.

08 / MEMORY

THE FIRST TASK LEARNS. THE SECOND REPLAYS.

  • One map per app and version, keyed by the title bar: screens, menu edges, the last click position that worked, how often it worked.
  • Each screen and target keeps one appearance per version, so a redesign adds a version instead of breaking memory.
  • observe: when the static crops match the frame byte for byte, the stored snapshot is used. Moved? Template match. Changed? Perceive, re-ground, rewrite.
  • A cold app gets a ≤ 45 s menu pre-warm; a task's trace is written back when it ends, so the next task replays it.

09 / DATA

SQL ON A CACHE, NOT OCR ARITHMETIC

  • The app's own change log, Bitácora de cambios, is the freshness probe: one screen per task says whether anything changed, for every entity at once.
  • Fresh? The question is a SQL query over JSON rows. Stale? Page the grid once into a staging table and swap it in only when the read is complete.
  • Several questions in one task: cached answers first, then one visit per screen, answers reported in the order asked.
  • After our own write: read the record back, check the log moved. The app always wins.

10 / THE CHANGE15:30

DRIFT IS DETECTED ON THE STEP AND REPAIRED INSIDE THE TASK

rungwhatbudget
0Re-identify the epoch: new map directory inheriting every node as stale and every edge as a hint, re-run the pre-warm≤ 10 s + pre-warm
1Re-ground in place: template match → fuzzy label → same role and cell → Jev at ≥ 0.8 → VLM on the marked image≤ 5 s
2Re-explore this screen only, write the new edges≤ 30 s
3Replan: one LLM call, another route or a free plan, rejoin when a known screen appears≤ 15 s
4Rank down, never delete0
  • Seven signals, any one fires: label not found · no effect · wrong known screen · unknown screen · version string changed · an edge that leads two places · most of the menu bar gone.
  • Cheap filters first: blocking dialog? overlay? data edge? Only then drift.
  • Every rung writes {signal, rung, via, confidence, before, after, cost_ms} to the log. The loop takes the step only after rung 3.

  • Drift is a function of (stored map, live screen), so we mutate a copy of the stored map and run the task suite against it.
  • One extra evaluator, ExpectedLogLines, asserts the lines above in every task's JSONL. Exit code non-zero when one is missing.
  • Offline, on the golden v3.9 test map with scripted models: this is the form the test suite runs. On the shipped V4.2 map it is a rehearsal, not a live proof.

15 / DEPLOY

ONE IMAGE, ONE WORKER, PER-TASK DESKTOP

  • python:3.12-slim + uv sync --frozen, uvicorn with one worker: task state and RFB sessions live in-process.
  • Railway builds from the Dockerfile and checks GET /health. Restart on failure.
  • The service refuses to start without TEAM_TOKEN, OPENROUTER_API_KEY and the three model ids. No model id is hard-coded.
  • The desktop URL and password arrive in POST /tasks, never from the environment. The /evals page is served by the same deploy.

[✓] WHAT THAT MEANS FOR THE DEMO
  • Every path above has a fallback that is itself logged: the loop, OCR paging, the default model.
  • Each item is one commit: a file, an include, a live run with --publish.
  • The design doc's §12 lists them next to what ships, so the claims and the gaps sit in one table.
